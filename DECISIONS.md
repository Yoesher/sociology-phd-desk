# Architecture Decision Records

This file records durable product and architecture choices. Each decision includes its date, decision, rationale, alternatives, and consequences. New entries are append-only; superseded decisions should point to their replacement rather than silently rewriting history.

## ADR-001 — Local-first core

- **Date:** 2026-08-11
- **Status:** Accepted
- **Decision:** Keep the complete core workstation usable without an account, application server, default cloud synchronization, telemetry, or AI API. Store research workflow records on the user's device and make explicit export the portability path.
- **Rationale:** Sociology projects often contain unpublished findings, sensitive fieldwork context, confidential peer review, and institutionally controlled data. A local-first core reduces unnecessary disclosure, lowers operational cost, supports offline work, and prevents a hosted service from becoming a prerequisite for basic research management.
- **Alternatives:** Server-first multi-user application; mandatory account and cloud sync; file-only desktop application; localStorage-only web application.
- **Consequences:** The project can run as a static client and does not need an account service. Users are responsible for device security and backups. Cross-device synchronization and collaboration are not automatic. The UI and documentation must never imply that local storage is encrypted, indestructible, or institutionally compliant by itself.

## ADR-002 — IndexedDB through Dexie for persistence

- **Date:** 2026-08-11
- **Status:** Accepted
- **Decision:** Use IndexedDB as the first persistence layer, accessed through Dexie. Keep a versioned domain schema and repository/data-access boundary rather than reading storage directly throughout page components.
- **Rationale:** The research model contains multiple related object types and will outgrow localStorage size, transaction, and query constraints. IndexedDB is broadly available in modern desktop browsers and supports structured, offline data. Dexie reduces transaction and migration complexity while retaining browser-local operation.
- **Alternatives:** localStorage; SQLite/WASM; a native desktop database; a remote relational database; direct IndexedDB calls without a wrapper.
- **Consequences:** Database upgrades require explicit migrations and tests. Browser storage quotas and deletion behavior remain user-visible risks. Persistence tests need `fake-indexeddb` or browser-level coverage. A future desktop wrapper can add adapters, but domain logic must not assume a server database.

## ADR-003 — React, TypeScript, and Vite client architecture

- **Date:** 2026-08-11
- **Status:** Accepted
- **Decision:** Build the initial client with React, TypeScript, and Vite; organize by application shell, reusable components, features, models, and data services rather than one large `App.tsx`.
- **Rationale:** The stack is mature, maintainable, suitable for a static offline-friendly browser application, and supports typed domain models, fast local development, testing, and a low-friction contributor path. Feature boundaries match the research lifecycle and can evolve independently.
- **Alternatives:** Vanilla TypeScript; Vue; Svelte; Next.js or another server-oriented framework; Electron-first desktop application.
- **Consequences:** The project accepts a JavaScript dependency ecosystem and must monitor supply-chain risk. React components must not become the persistence or domain layer. Server rendering is not a current requirement. Build compatibility is tied to supported Node and browser versions documented in the repository.

## ADR-004 — Complement Zotero; do not recreate it

- **Date:** 2026-08-11
- **Status:** Accepted
- **Decision:** Treat Zotero as the reference-library system of record. Sociology PhD Desk records why a work should be read, which project or question it informs, what analytical judgment follows, and whether it enters a manuscript argument. Any future Zotero integration must respect this boundary.
- **Rationale:** Bibliographic acquisition, deduplication, citation styles, attachments, and citation insertion are already deep specialist capabilities. Reimplementing them would dilute the product and create a high maintenance burden. The unmet need is research orchestration across literature and other research objects.
- **Alternatives:** Build a full reference manager; store only free-form literature notes; exclude literature entirely.
- **Consequences:** The initial literature object can store descriptive metadata but does not promise reference-library completeness. DOI and URL fields must not imply verification. Future integration needs official API and license review, conflict semantics, and clear ownership of edits.

## ADR-005 — Anonymous identifiers at the fieldwork boundary

- **Date:** 2026-08-11
- **Status:** Accepted
- **Decision:** Model field sites, cases, participants, interviews, and visits with anonymous IDs and aliases. Keep the warning “Do not store directly identifying participant information here” at relevant entry points. Do not add fields that solicit direct identifiers.
- **Rationale:** Direct identifiers increase harm if a device, browser profile, export, issue attachment, or repository fixture is exposed. The workstation can coordinate research without storing names, phone numbers, government identifiers, precise addresses, signatures, or full consent documents.
- **Alternatives:** Permit arbitrary personally identifying fields; encrypt identifiers inside the application; omit fieldwork support; rely only on a documentation warning.
- **Consequences:** Researchers must keep re-identification keys, consent records, and protected source material in institutionally approved systems outside the application. Anonymous IDs still may be linkable and are not automatically de-identified. Demo fixtures must be clearly synthetic. Encryption and ethics approval remain outside the product's guarantee.

## ADR-006 — Safe import: merge by default, replacement only by explicit choice

- **Date:** 2026-08-11
- **Status:** Accepted
- **Decision:** Validate the complete portable workspace envelope before writing. Default to a non-destructive merge flow that reports collisions and preserves existing records unless the user resolves them. Whole-workspace replacement is a separate, explicit action with a clear consequence and confirmation; it must never be triggered by ordinary import.
- **Rationale:** Research workspaces can represent months or years of work. Silent overwrite is unacceptable, and partial writes from malformed input make recovery difficult. A previewable, transactional import boundary supports portability without turning data migration into a destructive operation.
- **Alternatives:** Always replace; last-write-wins merge; import without validation; reject any workspace containing an existing ID; silently create duplicate IDs.
- **Consequences:** Import requires schema versioning, validation, conflict reporting, and transaction tests. Merge semantics may be more verbose for users. Replacement must remain visibly distinct in UI and tests. Exports should include a format version and enough metadata to validate compatibility, without adding identifying telemetry.

## ADR-007 — Source evidence and AI suggestions are different object classes

- **Date:** 2026-08-11
- **Status:** Accepted
- **Decision:** AI is optional and outside the core dependency path. Any generated output must be labeled as an AI-generated suggestion, retain relevant provenance and review state, and never automatically become source evidence or a verified finding.
- **Rationale:** Language-model output can be incomplete, incorrect, fabricated, or detached from consent and data-governance constraints. Sociology requires evidence provenance and accountable interpretation. Treating generation as evidence would undermine the product's central research-ethics and traceability goals.
- **Alternatives:** Make an AI assistant the primary interface; automatically add generated claims to the evidence ledger; exclude AI integrations permanently; treat AI and human notes identically.
- **Consequences:** Core workflows remain available offline without model access. Future AI interfaces need explicit consent, disclosure of any data leaving the device, provider/configuration boundaries, and review actions. Generated content cannot inherit a source locator or support level without a human linking actual evidence.

## ADR-008 — Original academic visual language

- **Date:** 2026-08-11
- **Status:** Accepted
- **Decision:** Use an original, calm, editorial, research-oriented interface with deliberate typography, quiet surfaces, clear rules, and dense-but-readable registries. Do not import a generic Bootstrap/admin-dashboard visual template or use emoji as the product's primary icon/status system.
- **Rationale:** The application supports sustained scholarly judgment, not operational monitoring or sales analytics. A distinctive academic visual system makes hierarchy and provenance legible while reinforcing the sociology-specific identity.
- **Alternatives:** Generic component-library defaults; colourful startup dashboard; document-editor clone; minimal unstyled forms.
- **Consequences:** New screens must reuse shared tokens and primitives and pass light/dark, responsive, keyboard, and density review. Originality does not justify decorative complexity: accessibility, focus, semantics, and information clarity remain hard constraints. See [DESIGN.md](DESIGN.md).

## ADR-009 — Chinese-first bilingual interface with locale-neutral research data

- **Date:** 2026-08-11
- **Status:** Accepted
- **Decision:** Use Simplified Chinese as the default application and repository entry language, and maintain a complete English interface. Store language preference separately from workspace research data. Keep identifiers, schema enums, import/export values, and persisted domain records locale-neutral. A language switch changes application chrome, system messages, dates, and number presentation, but never silently translates or rewrites user-authored research content.
- **Rationale:** The project is intended to be directly usable by Chinese sociology researchers while remaining accessible to international contributors and researchers. Treating translated labels as persisted values would make schemas language-dependent, break validation and portability, and risk corrupting existing work. Automatically translating research notes would also change authorship and analytical meaning without consent.
- **Alternatives:** English-only interface with a Chinese README; browser-language auto-detection as the sole default; separate Chinese and English applications; storing translated labels inside domain records; automatic translation of user content.
- **Consequences:** Every substantial interface feature must ship with aligned Chinese and English resources, including validation, accessible names, responsive table labels, dialogs, and recovery guidance. Tests must check message-key and interpolation parity, raw persisted values, language persistence, and unchanged user content. CJK and English layouts require responsive and accessibility review. Documentation may have language-specific entry files, but verified behavior and project status must remain consistent.

## ADR-010 — Compliance-gated, county-level China Research Map

- **Date:** 2026-08-11
- **Status:** Accepted
- **Decision:** Treat the China Research Map as a first-class sociology research capability for linking regional research notes and comparing coverage across province, prefecture, and county levels. Stop the supported hierarchy at county level and never collect, infer, display, or export exact participant locations. Do not implement or publish map boundaries until an authoritative, legally usable source has been verified and its provenance, permitted use, attribution, version, and update path are documented. Never substitute an arbitrary map dataset merely to make the feature visible.
- **Rationale:** Place and administrative context matter to comparative, population, labour, family, organizational, migration, and fieldwork research in China. At the same time, incorrect boundaries, unclear licensing, and overly precise participant geography create legal, maintenance, research-integrity, and re-identification risks. A decorative map without source discipline would weaken rather than strengthen the workstation.
- **Alternatives:** Omit geographic organization; use any convenient open boundary file; support point coordinates and street-level participant mapping; embed a mandatory commercial map service; implement a generic global map first.
- **Consequences (editorial correction and gate result, 2026-08-12):** Phase 3D—not Phase 3C—remains blocked until source and legal verification passes. The original Phase 3C label was a transcription error; this correction does not change the accepted map compliance gate. The feature must retain local-first operation, document attribution, support a useful non-map fallback, and model regions independently from translated display labels. Tests and review must cover administrative hierarchy, incomplete or changing codes, privacy boundaries, import/export behavior, accessibility, and graceful source failure. Exact household, interview, or participant coordinates are outside the product scope even when a researcher could technically provide them. The first formal review recorded all four mandatory gates as `BLOCKED`: no reviewed source currently supplies the required scope together with verified public-redistribution and transformation rights, the project has no final-output map-review metadata, and national completeness is therefore not testable. The evidence and unblocking requirements are maintained in [Chinese](docs/zh-CN/map-data-sources.md) and [English](docs/en/map-data-sources.md). ADR-015 supersedes only the release-sequencing consequence: the blocked map remains unimplemented, but it no longer gates non-map `v0.2.0` work.

## ADR-011 — Sociology-specific product structure and honest privacy boundaries

- **Date:** 2026-08-11
- **Status:** Accepted
- **Decision:** Adopt the following permanent product principles:
  1. Sociology PhD Desk is a sociology research workstation, not a general-purpose Todo application.
  2. Simplified Chinese is the default user language, and every substantial new UI feature must provide both `zh-CN` and `en` in the same change.
  3. Primary navigation represents domains of research work.
  4. Secondary navigation represents research workflows or smart views within a domain.
  5. Secondary navigation is normally a derived view or smart filter and must not be tightly coupled to database enums.
  6. A menu label is never, by itself, justification for adding a database status.
  7. The main sidebar has at most two navigation levels.
  8. The product must not grow an indefinitely nested third- or fourth-level navigation tree.
  9. Concrete projects, manuscripts, interviews, regions, and other research objects are explored further in the content area rather than by adding sidebar levels.
  10. UI language switching must never translate user-authored research content.
  11. A private local workspace is not a network account.
  12. The default remains local-first, with no account and no required cloud service.
  13. The product may claim that data is encrypted only when real data encryption is implemented; hiding or locking the UI alone is not encryption.
  14. The China Research Map is a primary, first-class module.
  15. Geographic research management stops at county level by default and does not descend to township, subdistrict, or village levels.
  16. Map notes, fieldwork material, and other user data must never be uploaded to GitHub Pages or a map service.
- **Rationale:** A durable information architecture must express sociology research work rather than reproduce a task manager's categories. Derived navigation lets researchers see useful workflow slices without making presentation labels part of the stored domain model. Clear local-workspace and encryption language prevents a browser-local application from implying accounts, cloud protection, or security properties it does not provide. The map is valuable only when it preserves administrative scope, data provenance, and the confidentiality of user research.
- **Alternatives:** Model the product as a generic Todo tool; map every navigation label to a persisted enum; allow arbitrary sidebar depth; treat a local lock screen as encryption; require accounts or cloud storage; send notes to a hosted map service; present the China map as a secondary visualization.
- **Consequences:** Feature proposals must identify the sociology workflow they support. Navigation changes require a derived-view assessment before any schema change, and drill-down belongs in page content after two sidebar levels. New interface work must remain bilingual and data-neutral. Private-workspace UX must not imply an online identity, and encryption wording requires actual, reviewed cryptography. The public static application may load approved map geometry but must not transmit user workspace data. For clarity, the China Research Map implementation phase is Phase 3D; ADR-010 now records the Phase 3C → Phase 3D phase-label correction explicitly without changing its compliance gate.

## ADR-012 — Stable first-class research questions and analytical claims

- **Date:** 2026-08-11
- **Status:** Accepted
- **Decision:** Introduce `ResearchQuestion`, `Claim`, and `ClaimQuestionLink` as first-class portable and persisted research objects. `ResearchQuestion` and `Claim` each inherit stable entity metadata (`id`, `createdAt`, `updatedAt`, and `isDemo`) and store `projectId`, `text`, `status`, and `notes`. Research-question statuses are `draft`, `active`, `addressed`, and `retired`; claim statuses are `draft`, `active`, `superseded`, and `retired`. `ClaimQuestionLink` inherits the same stable entity metadata and stores `projectId`, `researchQuestionId`, and `claimId`. Link endpoints must exist and all three records must belong to the same project; text is never a foreign key. A question or claim with incoming links cannot be deleted until those links are explicitly removed, and project deletion remains blocked while these dependent records exist.
- **Rationale:** Research questions and analytical claims evolve independently and have a many-to-many relationship. Stable IDs preserve identity while wording and status change, allow explicit links to be audited, and avoid treating prose equality as research meaning. Project scoping prevents accidental relationships between unrelated studies, while protected deletion preserves the interpretive trail.
- **Alternatives:** Keep questions and claims only as free text; use text as a key; infer links from semantic similarity; permit cross-project links; cascade-delete questions, claims, or links; postpone first-class objects until evidence linking is implemented.
- **Consequences:** The portable workspace format advances to v3 and migrations must compose deterministically as v1 → v2 → v3. v3 removes `Project.researchQuestion` after creating a `ResearchQuestion` in that project. During v2 → v3, each non-empty legacy `Evidence.claim` contributes to deterministic same-project claim creation; only byte-for-byte equality after trimming may be used for grouping, and the source-context `Evidence.claim` text remains present and is never semantically merged, fuzzily matched, or rewritten. Migration must not infer which research question a claim answers, so `claimQuestionLinks` starts empty for legacy data. Issue #2 remains responsible for any future explicit Evidence↔Claim relationship; v3 does not add an evidence `claimId`. Import validation and repository writes must reject missing endpoints, cross-project links, duplicate link pairs, and deletion that would orphan links. UI copy must explain that a claim is an evolving analytical judgment, not proof or statistical significance.

## ADR-013 — Password-encrypted local workspaces and backups

- **Date:** 2026-08-12
- **Status:** Accepted
- **Decision:** Implement encrypted workspaces and encrypted `.sociologydesk` backups only with the browser Web Cryptography API and fail closed when the required APIs or exact format are unavailable. This is application-layer encryption, not an account, cloud vault, operating-system key store, or compliance guarantee.
- **Cryptographic contract:** A passphrase is normalized to NFC and then encoded as UTF-8; it is never trimmed or case-folded. New passphrases contain 15–1024 Unicode code points after normalization. PBKDF2-HMAC-SHA-256 uses exactly 600,000 iterations and a fresh 16-byte random salt. It derives a non-extractable 256-bit AES-GCM `CryptoKey`. Every encryption uses a fresh random 12-byte IV and a 128-bit authentication tag. The canonical protected-header UTF-8 bytes are AES-GCM additional authenticated data (AAD). The passphrase, a verifier, and the derived key are never persisted. A key exists only in an unlocked JavaScript session and is discarded on lock, close, or reload; JavaScript cannot guarantee physical memory zeroization.
- **Versioned containers:** Container format v1 and portable workspace payload v3 are separate version domains. The local purpose is `encrypted-local-workspace`; the backup purpose is `encrypted-backup`. Local protected metadata is limited to application, purpose, container version, payload version, random UUID binding ID, storage revision, key invocation, KDF parameters (including salt and NFC marker), and cipher parameters. Backup protected metadata omits binding ID, workspace name, timestamps, and other research metadata. Protected headers are at most 8 KiB, ciphertext is at most 64 MiB, and content is not compressed. Local containers remain binary internally. Backup files are exact canonical JSON with the field order `protected`, `iv`, `ciphertext` and unpadded canonical base64url values.
- **Strict parsing and errors:** Unknown or missing fields, noncanonical JSON/header bytes, leading or trailing wrapper whitespace, invalid/noncanonical base64url, invalid salt/IV/tag/ciphertext lengths, oversize input, and unsupported container or payload versions are rejected. Wrong passphrases, authenticated-field or ciphertext tampering, and post-authentication payload, binding, revision, or invocation mismatches produce the same generic authentication failure. Decrypted content must pass the complete portable-v3 workspace validator before use.
- **Encrypted persistence:** One private IndexedDB contains exactly one ciphertext container plus plaintext coordination values: `storageRevision`, `lockEpoch`, committed `keyInvocation`, and monotonic `encryptionAttempts`. It contains no research-domain tables, workspace name, or content-derived verifier. Before every local AES-GCM encryption, a short independent transaction verifies the current committed coordinates and protected binding/salt generation, enforces the `2^32` limit, and durably reserves the next attempt number. The protected header uses that reserved number as `keyInvocation`; gaps are valid because a crash, encryption error, lock, or losing ciphertext CAS never rolls a reservation back. Encryption then runs outside IndexedDB, and the commit transaction checks the committed revision, lock epoch, invocation, and generation while preserving the greatest reserved attempt count. A lock verifies the same generation and atomically advances `lockEpoch`, so a delayed cooperating tab cannot commit after lock and a session from an explicitly reused binding cannot mutate the replacement vault. Creation is not publishable until an actual IndexedDB read-back decrypts, strictly validates, matches binding/revision, and is semantically equal to the requested workspace. Restoring an encrypted backup authenticates it before opening a destination database and requires a new logical workspace ID with storage revision zero.
- **Migration and deletion:** Plaintext-to-encrypted conversion is staged. Phase one writes a new encrypted vault, reads it back, decrypts it, validates it, and only then publishes the encrypted registry route while retaining the old plaintext workspace as a recovery source. Phase two is a later, separately recorded cleanup after the encrypted route has been verified and opened. Physical IndexedDB deletion and registry publication cannot be one atomic transaction: a deletion failure leaves the recorded source pending, while a failure after physical deletion can also leave a conservative `cleanup-pending` marker until an idempotent retry verifies absence and finalizes it. The marker therefore records what the application has verified, not a forensic assertion that bytes do or do not remain. Deleting an IndexedDB database is logical deletion, not verifiable secure erasure: browser storage, filesystem snapshots, synchronization, backups, and flash wear levelling may retain recoverable remnants.
- **Rationale:** AES-GCM supplies authenticated encryption and is directly specified by [W3C Web Cryptography](https://www.w3.org/TR/webcrypto/#aes-gcm) and [NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final). Password-derived storage keys and salts follow [NIST SP 800-132](https://csrc.nist.gov/pubs/sp/800/132/final). [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) currently recommends Argon2id generally and lists PBKDF2-HMAC-SHA-256 at 600,000 iterations for PBKDF2/FIPS-oriented use. Argon2id was not selected for v1 because it is not exposed by Web Crypto; a WASM implementation would add a separate cryptographic implementation, supply-chain surface, memory tuning, and interoperability contract. PBKDF2 is the most auditable browser-native choice for this release, but the work factor and a future memory-hard container version require periodic review. [OWASP Cryptographic Storage](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html) informs algorithm, threat-model, and key-lifetime choices.
- **Alternatives:** Argon2id in WASM; scrypt in WASM; an envelope-encryption design with a random data-encryption key; OS/desktop keystore integration; server-managed keys; UI-only locking; plaintext IndexedDB; noncanonical or self-describing containers. Argon2id and envelope encryption remain candidates for a new, explicitly versioned container rather than an in-place reinterpretation of v1.
- **Consequences and limitations:** A locked ciphertext raises the cost of offline disclosure but cannot make a weak passphrase strong. All scripts, service workers, extensions, and compromised dependencies able to execute with the application’s origin are within the trust boundary; path-based applications on a shared origin are not isolated from one another by the same-origin policy. While unlocked, same-origin malicious code, browser compromise, malware, an administrator, or a compromised device can capture plaintext or passphrases. `lockEpoch` coordinates cooperating application tabs and invalidates later repository writes and backups when they observe it; it does not remotely overwrite plaintext or key references already held by every tab and is not an access-control boundary against hostile same-origin code. The separate plaintext registry contains operational metadata including logical IDs, display names, storage locators, mode/state, revisions, timestamps, auto-lock settings, and migration/cleanup/provisioning state, but no research body or content-derived hash. Authentication protects an individual container but does not supply a trusted monotonic counter, so replacing storage with an older complete valid container can roll the workspace back. The feature does not prevent browser-profile deletion, disk failure, traffic analysis from file/database size, screenshots, clipboard exposure, or loss caused by a forgotten passphrase. There is no password reset or recovery key in v1. Security copy and privacy documentation must state these boundaries without claiming “zero knowledge,” “military grade,” absolute safety, secure erase, or institutional compliance.

## ADR-014 — Metadata-only registry and isolated per-workspace persistence

- **Date:** 2026-08-12
- **Status:** Accepted
- **Decision:** Replace the runtime singleton-database assumption with one plaintext schema-v1 local registry and a physically separate database for every logical workspace. The registry owns routing and recoverable lifecycle state only. Each ready entry maps a stable logical workspace ID to an opaque `storageId`, a `standard` or `encrypted` adapter, and a `personal` or `demo` kind. Standard workspaces use the existing 17-table IndexedDB schema v3; encrypted workspace persistence follows ADR-013. Portable research data remains `WorkspaceData` v3 and is not embedded in the registry. A fresh installation deterministically provisions one empty personal workspace and one distinct, exactly pristine synthetic demo so concurrent first-boot callers converge on the same routes.
- **Registry boundary:** Plaintext registry metadata includes the canonical display name, timestamps, mode/kind, auto-lock choice, portable and storage schema versions, optimistic registry revision, lifecycle state, migration/cleanup truth, an optional durable `encryptedConversion` target reservation, and opaque storage locators. It excludes research-domain collections, passphrases, derived keys, password verifiers, and content-derived hashes. Registry metadata may itself be sensitive and is not protected by workspace encryption. Export copies the canonical display name into a generated portable or encrypted payload without rewriting the active domain snapshot or advancing its workspace-data revision; a separate best-effort last-export metadata update may still advance the registry revision. Independent database names prevent accidental application joins; they do not create independent Web security origins.
- **Bound repository and session rule:** Research routes mount only behind an unlocked workspace session, and all domain writes pass through a repository bound to one logical workspace and one current registry route. Complete workspace validation rejects cross-workspace identities and endpoints. A bound standard repository must never provision or recreate missing storage during an ordinary read, replace, merge, or stale-session write; only an explicit provisioning path may create a database. A missing standard database, missing encrypted-vault record, authenticated vault tamper, invalidated registry route, or manager close poisons/closes the affected session and clears its cached snapshot. Encrypted asynchronous refresh/save/backup/lock work also carries a lifecycle generation; close or lock advances it, and every later state publication rechecks it, so a delayed decrypt cannot revive a closed session. Switching, locking, conversion, cleanup, or deletion likewise closes the old route so it cannot continue through the cooperating application.
- **Provisioning and deletion recovery:** Registry states are `provisioning`, `ready`, `migration-failed`, and `deleting`. Ordinary logical IDs, opaque storage locators, provisioning tokens, and encrypted bindings require cryptographically secure browser randomness and fail closed if it is unavailable; deterministic first-boot locators are convergence coordinates, not secrets. Before any provision or migration creates storage, physical preflight and unified database-name ownership/alias rules check ready and non-ready routes, conversion targets, retained plaintext sources, migration ledgers, the registry name, reserved prefixes, and existing physical databases. The application must not clear an unknown, mismatched, multi-workspace, or otherwise claimed database. A route becomes `ready` only after physical read-back, strict validation, identity checking, and semantic equality. Deletion first publishes a `deleting` tombstone, then removes only the owned physical storage, verifies its absence, and only then removes the registry entry. Bootstrap automatically retries tombstones when cross-tab-safe locking exists; unresolved deletions remain visible in Workspace Center for an explicit idempotent retry.
- **Legacy migration:** Treat the former `sociology-phd-desk` singleton as a read-only recovery source. A deterministic ledger keyed by source database, logical workspace identity, schema, and revision coordinates idempotent v1/v2/v3 migration. Copy into a fresh isolated standard database, close/reopen it, read it back, strictly validate it, and compare it semantically before publishing a ready route. Re-read the source before publication so a concurrent source change cancels promotion. Only an exact pristine bundled fixture is classified as `demo`; an edited legacy demo is personal research data and bootstrap creates a separate pristine demo. A failed, interrupted, repeated, or source-raced migration retains the legacy database and records a recoverable outcome. The application never automatically deletes that legacy source; any later cleanup is explicit, independently verified, and cannot be described as secure erasure.
- **Conversion and plaintext cleanup recovery:** Standard-to-encrypted conversion reserves a fresh encrypted target durably in the standard registry route before target creation. If interrupted staging exists, retry must authenticate it with the supplied passphrase, verify its workspace identity, and compare it with the current standard source before promotion. Discarding an existing staged vault requires the same authentication and identity proof; only a confirmed-absent target can have its empty reservation cleared without a passphrase. Promotion records the standard source as retained. Later cleanup first flushes pending UI/repository writes, requires the current unlocked encrypted session, and acquires the encrypted target and plaintext source by their actual database names in one stable lexical lock order. While both locks remain held, it rereads/authenticates the current vault, rechecks the route, and verifies the source locator is unshared and its stored logical workspace identity matches before physical deletion and registry finalization.
- **Cross-tab coordination:** Use a workspace-scoped exclusive Web Lock for standard writes and for route-changing/destructive operations. Re-read the registry route inside the lock before touching storage. Conversion, plaintext cleanup, provisioning discard, deletion, and deletion-finalization fail closed when cross-tab-safe locking is unavailable. A content-free `BroadcastChannel` message may improve refresh/lock UX, but it is not the correctness primitive and must never contain research content, passphrases, or keys. Encrypted-vault lock/revision/invocation coordination is specified separately by ADR-013.
- **Rationale:** A sociology researcher may need to separate projects, methods, clients, fieldwork contexts, or a synthetic tour without creating an online account. Physical adapters plus logical identity checks make accidental data mixing and stale-route writes easier to prevent and test. Explicit lifecycle states make browser crashes and non-atomic IndexedDB deletion/recovery honest. Retaining a verified source until a new route is known-good protects long-lived research data from one-shot migration failures.
- **Alternatives:** Keep one singleton and add a `workspaceId` column to every table; store all workspaces as one large JSON record; encode workspace display names into database names; use `BroadcastChannel` alone for mutual exclusion; silently recreate a missing database; automatically delete legacy/plaintext sources after copying; require an account and remote database.
- **Consequences:** The browser profile contains more IndexedDB databases and a visible routing registry. Lifecycle, interrupted-conversion, deletion-recovery, and cleanup UX are more explicit, and retained recovery sources can continue to expose plaintext until the user completes a separately authenticated and verified cleanup. Browsers without Web Locks may still open ordinary workspaces, but destructive cross-tab transitions are unavailable rather than weakly emulated. Registry schema v1, standard database schema v3, encrypted-vault database schema v1, encrypted container v1, portable workspace v3, and the package version evolve independently. This remains local-first software with no account, required cloud service, automatic backup, secure-erasure guarantee, or cross-origin isolation promise.

## ADR-015 — Defer the China Research Map from v0.2.0

- **Date:** 2026-08-12
- **Status:** Accepted
- **Decision:** Preserve the Phase 3D source and compliance audit, keep all four map gates `BLOCKED`, and defer the China Research Map outside the `v0.2.0` release scope. The blocked result prevents map geometry, administrative production data, region persistence, and public map deployment; it does not block the Theory Research workspace, hierarchical navigation, publishing integration, release stabilization, or `v0.2.0`. Close Issue #8 as not planned for the current release; it may be reopened only if a suitable public source and project-specific approval conditions can be verified.
- **Rationale:** A map can be drawn technically, but the reviewed source, redistribution, transformation, and final-output approval conditions do not form a sufficiently verified and maintainable chain for an open GitHub repository and GitHub Pages deployment. Continuing to search or substituting an arbitrary dataset would expand schedule and compliance risk without strengthening the core sociology research workflow. The release can deliver coherent theoretical, research-graph, private-workspace, navigation, and publishing improvements without geography.
- **Alternatives:** Keep the entire release blocked indefinitely; ship an unverified or decorative map; remove the compliance record; abandon all future geographic research support.
- **Consequences:** `v0.2.0` has a fixed non-map scope. The bilingual source register and no-geometry decision remain durable evidence. The map is described as deferred—not implemented, failed, illegal, or impossible—and may return in a later roadmap only after independent verification. No later release work may weaken ADR-010's provenance, participant-location, local-first, or approval requirements.
